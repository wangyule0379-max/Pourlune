# Pourlune 首版技术方案 v1.0

确认日期：2026-10-21（Asia/Taipei）  
状态：用户已确认技术方向，作为首版实现基线；尚未完成 App 实现、SDK 接入或真机验证。  
发行范围：海外市场，iOS 与 Android。

首版采用 Flutter、纯 Dart 游戏逻辑、SQLite 本地存档，以及 Firebase 和 AdMob 托管服务。题库随安装包发布，核心玩法离线可用；不自建业务服务器，不提供账号与跨设备云存档。卸载、清除数据或换机可能丢失进度和收藏，不承诺应用内云端恢复。

## 2. 技术选型

| 层级 | 首版选择 | 职责 |
|---|---|---|
| 客户端 | Flutter，iOS / Android | 页面、导航、交互、无障碍和平台适配 |
| 游戏呈现 | 分层静态美术资源＋局部 CustomPainter 动画 | 瓶体、液体、液面、符号和倒水动画 |
| 游戏核心 | 纯 Dart | 合法操作、倒入量、胜利、撤销、重开和加瓶规则 |
| 提示求解 | Dart isolate | 对当前局面执行可取消、有时限的搜索 |
| 本地数据 | SQLite，使用 sqflite | 实例、进度、收藏、设置、奖励和广告记录 |
| 崩溃监控 | Firebase Crashlytics | 崩溃、异常及必要的排查上下文 |
| 产品分析 | Firebase Analytics | 教学、通关、提示、流失及广告效果事件 |
| 远程配置 | Firebase Remote Config | 预先定义的广告开关、问题内容停用与恢复 |
| 广告 | Google AdMob，使用 google_mobile_ads | 插屏与玩家主动选择的激励广告 |
| 支持内容 | 静态网站＋反馈邮箱 | 隐私政策、帮助、反馈入口 |

首版不引入 Flame、实时 3D 或真实流体模拟。静态网站的托管供应商、域名与邮箱地址在发布准备时落实；具体 SDK 版本和最低系统版本在工程初始化及设备验证时确定并锁定，不在此文中虚构已验证版本。

## 3. 客户端结构与状态边界

采用呈现、应用流程、游戏核心、数据与外部服务四个职责边界，保持实现规模适合首版。

| 模块 | 负责 | 依赖约束 |
|---|---|---|
| 页面与绘制 | 渲染状态、接收点击、播放动画、提供语义和点击区域 | 不自行发奖或修改通关记录 |
| 应用流程 | 实例切换、结算、保存、提示任务、广告后的恢复与导航 | 协调核心与存储，集中处理异步结果 |
| 游戏核心 | 根据当前棋盘产生合法的新状态和结果 | 不依赖 Flutter、广告 SDK、数据库或网络 |
| 数据与外部服务 | SQLite、内置题库、广告、配置、统计与崩溃服务 | 向应用流程返回明确结果，不直接驱动页面导航 |

一次合法操作只提交一次完整棋盘状态，动画负责呈现前后变化；动画中途切后台不能留下半瓶状态或重复倒水。保存失败时保留内存中的完整结果，遵循产品规格的 Retry / Stay here 流程；不得将尚未落盘的结果显示为已安全保存。

提示从当前棋盘求解，不能直接套用初始参考解。搜索任务携带实例和棋盘修订标识，取消、重开、撤销或切换实例后丢弃过期结果。固定目标标签必须参与状态判断；不能把目标不同的瓶子错误地合并为等价状态。响应与搜索预算沿用产品补充稿，最终以设备测试验证。

## 4. 美术资源与性能

复用已确定的浅蓝、奶油针织、浅色液体及形状辅助视觉。房间、家具、瓶套、玻璃边缘和阴影拆为可复用资源；液体、形状、选中状态和水流独立绘制。文字、按钮和动态数字使用真实组件，不能把整张设计图当作可交互页面。

六瓶采用 3＋3，七瓶采用 4＋3，各行瓶体保持相同尺寸与容量比例。重绘局限在变化区域，静态资源缓存复用；减弱动效模式保留结果反馈并降低运动幅度。点击区域与无障碍语义独立于装饰图层。

以原设计的 60fps 为目标，在 profile / release 模式及实际目标设备上验证。UI 静态稿通过不等于帧率、大字号、屏幕阅读器或 SDK 流程通过。

## 5. 本地存档与一致性

保留一个普通活动实例槽和一个每日活动实例槽。完成记录、解锁、收藏及广告记录独立于活动槽，不因切换或重玩覆盖。

| 数据 | 必须保留的身份与信息 |
|---|---|
| 游戏实例 | instance_id、模式、稳定题目 ID、内容版本、初始题目定义、当前棋盘、步数、撤销历史、额外瓶状态 |
| 主线进度与收藏 | 首次完成的 level_id、解锁记录、拼片归属、结算回执 |
| 每日挑战 | puzzle_date、创建时区、目录版本、题目身份、完成与印章记录 |
| 广告奖励 | attempt_id、instance_id、领取意图、确认状态、发放状态及恢复所需实例快照 |
| 广告频控 | 累计首次通关计数、最近实际全屏展示时间 |
| 设置与迁移 | 用户偏好、隐私选择的适当状态、数据库 schema 版本 |

具体表结构在实现时落实，以上为数据契约，不要求每行拆成单独一张表。

通关事务原子写入完成记录、下一关解锁、拼片、广告计数与结算回执。奖励按领取请求与实例去重，并额外保证每个实例最多获得一个额外瓶；重复回调、重试和重启不得重复发奖。

按动作保存，不按动画帧保存。应用升级执行数据库迁移并验证旧存档，禁止以清空玩家数据作为常规升级策略。损坏恢复优先使用最近有效快照，不因单局损坏清空有效收藏。系统备份不作为跨设备恢复承诺。

## 6. 内置题库与每日挑战

首版交付 60 道主线题及至少 30 道已验证每日题。题目采用带版本的结构化数据，包含稳定 ID、容量、初始棋盘、目标标签和可回放参考解；所有题目须在不依赖广告额外瓶的条件下通过解题验证。

题目随 App 更新发布，首版不做远程关卡下载。已开始的实例保存完整题目定义与版本，继续、撤销和重开沿用原定义；更新题库不改写进行中的局面或已获得的收藏。

每日挑战沿用设备本地日历日期及固定日期映射目录，记录 epoch_date、目录版本和循环顺序；题库耗尽后按已验证目录循环。相同日期、相同目录版本选到相同题目，印章按日期去重。跨日继续、今日重玩和替换确认沿用产品规格。首版接受设备日期可被修改的边界，不加入联网校时、排行榜或竞技公平性保证。

## 7. 托管服务与离线行为

| 服务 | 使用边界 | 不可用时 |
|---|---|---|
| Crashlytics | 排查崩溃与异常，避免记录玩家敏感信息或完整反馈内容 | 不阻塞启动或游戏 |
| Analytics | 按产品规格记录必要事件，曝光以实际展示为准 | 游戏继续，不以事件上传成功作为结算条件 |
| Remote Config | 使用类型明确、可验证、有默认值的参数 | 使用上次有效配置或内置默认值 |
| AdMob | 请求状态允许后加载，在产品规定入口展示 | 不阻止免费提示、撤销、重开和通关 |
| 支持网站与邮箱 | 提供隐私说明和反馈渠道 | 不影响本地玩法 |

远程配置只控制客户端预先实现的行为，不作为存档数据库或可执行代码入口。配置在安全边界生效，不在进行中的局面里改题、改奖励或移除瓶子；广告关闭阻止后续请求与展示，但不能取消已确认的奖励。问题关卡停用应提供明确的暂不可用反馈，不删除进度或自动跳关。

初始化本地题库和存档后即可进入核心游戏，联网服务异步初始化。隐私选择界面放在稳定页面；广告请求和统计采集分别遵循适用的用户选择，不把 UMP 状态等同于所有服务的采集授权。具体地区流程、UMP、适用的 ATT 及商店披露在 SDK 接入和发布阶段核验。

## 8. 广告与奖励

广告由集中模块管理就绪状态、授权、冷却、展示互斥、回调、奖励和导航恢复。页面只表达用户意图，不各自维护频控计数。

首版采用 SDK 有效获奖回调确认额外瓶，不建设服务端奖励验证接口。展示前保存领取意图；获奖确认后持久化确认与发放结果，按实例去重。关闭广告不代表获得奖励。确认已收到但保存失败时进入待保存状态；若进程退出前既未收到也未持久化确认，不承诺可以恢复奖励。

频控沿用产品补充稿：前 10 关无插屏，之后自上次实际插屏累计至少 3 次主线首次通关才具备资格，最早第 13 关；未展示保留计数。任意全屏广告实际展示后的共享间隔为 180 秒。奖励广告不清零主线计数，重玩和每日不增加该计数；不在游戏中、首页或迟到加载时补弹。

第 20／40 关章节保护及其他补充规则的状态以产品补充稿为准；会话或滚动时段次数上限仍需后续单独确定。服务端验证仅在未来奖励价值、作弊风险或云端权益需求变化时评估。

## 9. 首版服务端范围与后续扩展

首版不采购业务云主机，不部署业务 API，不建设云数据库、账号系统、云存档、远程题库后台或自研运营后台。托管平台控制台承担首版监控和配置工作。正式接入前准备 Firebase 项目、AdMob 应用与广告位、支持域名和反馈邮箱；开发使用测试广告，配置与生产环境区分。

| 未来需求 | 届时增加的能力 |
|---|---|
| 换机恢复、跨设备同步 | 身份识别、云存档、版本冲突与合并规则 |
| 不发版增加关卡 | 内容清单、对象存储 / CDN、完整性校验与回退 |
| 高价值奖励或云端权益 | 服务端验证、奖励账本和去重接口 |
| 统一每日赛程或排行榜 | 服务器时间、题目接口与成绩验证 |

以上为扩展条件，不计入首版开发承诺。

## 10. 实现顺序与验收门槛

1. 用真实分层资源验证六瓶倒水、撤销、七瓶同尺寸、保存和强制退出恢复，尽早确定渲染与数据方案可行性。
2. 完成纯 Dart 核心与题库验证工具，再接通主线、每日、收藏和本地事务。
3. 接入并验证提示求解的取消、超时和过期结果处理，完成 UI 增量对应状态。
4. 接入托管服务、隐私选择与测试广告，覆盖离线、回调乱序、重复回调、保存失败和进程中断。
5. 对照产品验收矩阵执行真机、窄屏、大字号、减弱动效、辅助功能及性能验证。

关键验收证据包括：题库参考解回放；规则与撤销正确性；通关事务及奖励幂等；升级后存档恢复；无网络可完成核心流程；广告失败不阻塞免费玩法；过期提示不作用于新局面；动态液体与分层素材的实际设备表现。文档确认不代表以上检查已通过。
