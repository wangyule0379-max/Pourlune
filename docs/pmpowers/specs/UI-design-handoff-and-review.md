## 3. 不可混淆的业务规则

1. 目标瓶装满对应颜色且所有缓冲瓶为空才胜利；UI 不得仅因所有瓶单色显示完成。此条件已与原 PRD §2.4 核对。
2. 提示只建议一步，自动选源，玩家点目标才倒入；超时不等于无解。
3. 结算顺序为保存成功、通关与奖励展示、玩家导航意图、合格广告检查、下一局。
4. 插屏最早第 13 关，自上次实际插屏后累计至少 3 个首次通关；未展示保留资格，下次新结算可检查；首页及游戏中不补弹；20／40 章节保护是本次补充，重玩和每日不触发。
5. 共享 180 秒全屏展示时间间隔和每实例 1 个广告瓶已在原方案中存在；不是仅累计前台游戏时间。1–3 关隐藏激励入口，P16 保留两步确认。
6. 重开保留本实例额外瓶，撤销不收回瓶；达到上限不得继续显示可观看加瓶。
7. 旧每日局和今日新局共用一个每日槽，替换前须明确后果；印章属于题目日期；当天完成后的 Replay 保留且不重复发章。
8. 保存失败、奖励待处理和已经到账必须有不同反馈，不能只使用通用成功提示。

若执行聊天取得原始最新规则，与本次补定冲突，先记录到交付说明并由本聊天裁定；不得悄悄选择一个版本。

## 4. 交付物

在项目内保存成果，建议目录为 docs/design/，保持原素材路径可追溯。

| 交付物 | 要求 |
|---|---|
| 原件与版本清单 | 原设计来源、文件路径／链接、页面编号、缺失原件列表 |
| 页面状态矩阵 | UI-01～12 每项列出已覆盖／本次新增／受阻及对应稿件或截图 |
| 设计稿或原型 | 可打开查看；每项状态有明确名称，可重现或直接定位 |
| 逐步证据 | 关键流程截图、状态说明、按钮结果；截图必须来自实际交付的设计／原型 |
| 文案与组件补充 | 英文文案、字号／间距／颜色／状态组件沿用依据，避免另立风格 |
| 交付说明 | 变更清单、已完成项、已验证项、尚未验证项、原文冲突和打开方式 |

静态稿可以证明视觉覆盖，不证明点击、存档、SDK 和恢复功能已实现。原型模拟的广告或异常须在交付说明标注，不应被误认为真实 SDK 验证。

## 5. 验收流程

由本聊天独立打开交付物，使用产品设计审查方法查看真实截图或操作原型。执行聊天自查是交付输入，不直接作为最终通过结论。

### 5.1 覆盖与一致性

- UI-01～12 每项有证据或明确阻塞，不能只写“已处理”。
- 已有 P01～P21 的编号对照清楚；新增状态附着在对应页面，不随意增加导航层级。
- UI 文案、按钮、数字和禁用行为与产品规格一致。
- 原稿视觉风格、瓶子可读性、收藏进度和交互组件保持一致。

### 5.2 必走流程

| 流程 | 逐步检查 |
|---|---|
| 普通首次通关 | 进入第 11 关、操作、保存、结算、下一关；不出现广告机会 |
| 拼片与广告重合 | 第 16 关保存、拼片完整展示、Next、广告关闭／失败、进入 17 关 |
| 加瓶后立即通关 | 激励入口、奖励待处理／到账、额外瓶、通关、插屏冷却跳过 |
| 跨日未完成 | 昨日局日期、继续／替换选择、取消确认、完成旧题、进入今日 |
| 结算中断 | 保存失败、重试、奖励动画中断恢复；不出现漏奖或重复成功提示 |
| 主线最终完成 | 第 60 关、完整收藏、全通首页、今日已完成、重玩后继续 |

### 5.3 视觉与可用性

按最终平台和设计基准尺寸验收；至少检查基准手机视口、窄屏和最大支持字号。检查安全区、底部按钮、长文案、弹窗滚动、液体颜色与形状、空瓶、选中状态、禁用状态、动效减少模式。截图能证明的项目与仍需真机验证的项目分开记录，不据静态稿宣称完整无障碍通过。

## 6. 缺陷分级与结论

| 级别 | 例子 | 处理 |
|---|---|---|
| 阻塞 | 原稿缺失导致无法核验风格、关键流程打不开、核心状态完全缺稿 | 不通过相关范围，明确所缺证据 |
| 严重 | 保存失败仍显示已保存、错关加瓶、跨日替换无说明、广告遮断章节奖励 | 必须修复后重验 |
| 一般 | 文案溢出、按钮状态不清、辅助入口难找、收藏不同页进度不一致 | 交付前修复 |
| 建议 | 非关键动效或可选装饰细节 | 可记录后续，不阻塞主流程 |

验收报告逐项给出：任务编号、证据路径、观察结果、问题级别、修复要求、复验结果。结论只能为通过、部分通过或未通过，并明确覆盖的是设计、原型还是运行中的 App。
